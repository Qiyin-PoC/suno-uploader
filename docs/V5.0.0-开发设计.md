## 1. 功能一：多音频排队批量上传

### 1.1 方案选型（重要）

采用 **主进程队列调度，每个文件独立 spawn 一次 backend 进程**，而不是在 backend 内部循环。

理由：
1. `run_upload` 内部多处 `os._exit(0)`（`main()` 的 catch 分支），在进程内循环调用会破坏退出语义。
2. 进程隔离：一首歌失败/崩溃不污染后续队列。
3. 每首歌天然继承现有 `workdir`、续传（`find_resume_run`）、历史（`history_store`）逻辑，零改动。
4. 停止语义清晰：杀当前进程即可，队列本身保留。

### 1.2 改动点

**`electron/main.js`**

- 新增状态：`let uploadQueue = []`、`let currentQueueId = null`、`let queueStopped = false`。
- `runStreaming` 增加可选第 4 参数 `queueId`，在 `send('backend:event', ...)` 转发时附加 `queueId` 字段；`backend:exit` 也带 `queueId`。
- `backend:upload-batch`（新 IPC）：接收 `[{path,title,speed}]`，构造队列项（`id/name/status`），`queueStopped=false`，调 `startNextQueueItem()`。
- `startNextQueueItem()`：取队首 pending 项 → 置 `uploading` → `runStreaming([...], queueId)` → 通过 `send('backend:queue', {...})` 广播队列快照。
- `backend:exit` 里：若当前 queueId 的进程退出 → 按「退出前最后一次 `result`/`failed`/`cancelled` 事件」更新该队列项状态（done/failed/cancelled），`currentQueueId=null`；若 `!queueStopped` 则 `startNextQueueItem()`。
- 新增 IPC：`backend:queue-remove(id)`、`backend:queue-clear`、`backend:queue-status`（`ipcMain.handle` 返回 `uploadQueue`）。
- `backend:stop`：除 kill 当前进程外，把当前队列项标记 `cancelled`，`queueStopped=true`（用户再点开始则重置）。
- `dialog:choose-audio` 增加 `properties: ['openFile','multiSelections']`，返回数组。

**`electron/preload.js`**

新增桥接：
```js
uploadBatch: (list) => ipcRenderer.send('backend:upload-batch', list),
queueRemove: (id) => ipcRenderer.send('backend:queue-remove', id),
queueClear: () => ipcRenderer.send('backend:queue-clear'),
queueStatus: () => ipcRenderer.invoke('backend:queue-status'),
onQueue: (cb) => ipcRenderer.on('backend:queue', (e, d) => cb(d)),
```

**`electron/renderer/renderer.js` + `index.html`**

- `state.queue = []`；`setAudio(path)` 改为 `addToQueue(paths)`；`drop` 取 `e.dataTransfer.files` 全部。
- 新增队列列表 UI（在 uploadPage 的 drop-card 下方）：每行显示文件名、状态徽标（待上传/上传中/完成/失败）、错误摘要、可单行移除；顶部「清空队列」。
- `startUpload()` 改为 `api.uploadBatch(queue.map(q => ({path, title: 文件名stem, speed})))`。
- 批量模式标题策略：默认每首用**文件名 stem**（竞品行为），保留单首模式下的 `titleInput` 仅对单文件生效。
- `handleBackendEvent` 增加 `backend:queue` 事件处理：更新 `state.queue` 渲染 + 进度。
- 完成语义：单曲 `result` 事件仍按现有逻辑（打开 Suno 页面改为「可配置」，批量模式默认只更新队列、不自动打开外部页面，避免弹一堆标签页）。

### 1.3 数据结构

```jsonc
// 队列项（主进程内存态 + backend:queue 快照）
{
  "id": "1735700000000-0",
  "path": "C:/.../song1.mp3",
  "name": "song1.mp3",
  "title": "song1",
  "status": "pending",        // pending|uploading|done|failed|cancelled
  "error": null,
  "songUrl": null,
  "elapsedSec": null,
  "workDir": null
}
```

### 1.4 风险

- 批量模式下「打开上传页面」行为变化，需保留手动按钮。
- 停止语义要覆盖「停止当前 + 停止后续」和「仅跳过当前」两种预期——v1 只做「停止当前+队列暂停」，点开始继续剩余。

## 2. 功能二：稳定上传速度调优（目标 6–10 分钟/首）

### 2.1 现状与瓶颈

稳定模式：`concurrency=3`，`upload_lane_policy(stable)=2→3`，`split_params_for_speed(stable)=target 4.8s/max 5.2s`。
一首 3 分钟歌 ≈ 37 段；每段 Suno 处理 ~10s；2–3 路并发 → 纯上传阶段就 ~3–4 分钟，再加渲染/轮询，才到「6–10 分钟」上沿。

三个杠杆，按性价比排序：

### 2.2 改动点

**（A）整首直传优先（杠杆最大，代码已存在）**

- `backend.py:run_upload` 中 `try_direct_whole_upload` 的触发条件（`GAOBAI_ENABLE_DIRECT_UPLOAD == "1"` 且非 onbeat2x）已是全局开启（`main.js` 已设）。保持，但把稳定模式直传失败的降级日志再明确一点（已存在）。
- 实测重点：**直传成功率**。若成功，一首歌 ≈ 1 次上传 + 1 次 feed 查询，稳稳进 6 分钟内。直传失败的主因是「Suno 拒收整曲」，此时才走切片。

**（B）减少稳定模式段数**

- `backend.py:split_params_for_speed`：`stable` 分支从 `target 4.8/max 5.2` 改为 `target 8.0/max 9.0/overlap 0.06`（段数约减半）。段变长会略升拒收率，但已有 `split_failed_segment_smart` 智能细切兜底。
- 注意：`onbeat2x` 和 `fast`/`experiment` 分支**不动**，避免回归。

**（C）稳定模式并发爬升更快**

- `backend.py:upload_lane_policy`：`stable` 分支 `initial 2→3`，`raw_steps [(7,3)]→[(5,4)]`。
- `backend.py:run_upload`：`stable` 的 `concurrency 3→4`。

**（D）给稳定模式加「温和版初始化闸门」，降低 429 硬等待**

- 现状 `UploadInitGovernor` 仅 `experiment` 启用，触发 429 后有 60–85s 硬等待，这是稳定模式偶发变慢的主因。
- 改动：`UploadInitGovernor` 增加 `mode` 参数，`stable` 模式用更松的参数（`base_interval_sec=8.0`、`throttle_hold_sec=45.0`、`repeated_throttle_hold_sec=60.0`），在 `run_upload` 中当 `speed=="stable"` 时也启用。

### 2.3 参数化与开关

新增环境变量（`main.js:backendEnv` 注入，默认关闭新值，等价旧行为，方便回滚）：
```js
GAOBAI_STABLE_TARGET_SEC  // 默认 8.0
GAOBAI_STABLE_MAX_SEC     // 默认 9.0
GAOBAI_STABLE_CONCURRENCY // 默认 4
GAOBAI_STABLE_GOVERNOR    // 默认 '1'
```

### 2.4 风险与验收

- 必须实测：对比「段数减半 + 并发 4」是否触发更多 429。若 429 变多，回退（C）到并发 3、保留（D）闸门。
- 验收口径：同一首歌，稳定模式端到端 elapsedSec 分布中位数 ≤ 600s。

### 3.4 「无限制」与「转 WAV」的边界（务必按此口径）

- **无限制**：单账号受自有曲库 + 积分 + 限流约束，无法做到字面「无限制」。真正的规模来自功能四多账号轮换。本模块支持「指定当前账号」下载，为多账号轮换预留 `--account` 参数。
- **转 WAV**：实现为「ffmpeg 重编码为 WAV」，文案只写「转码 WAV」，**不承诺/不宣传「洗水印」**。重编码会丢弃 MP3 的 ID3 元数据；音频域水印不在可控范围。

## 4. 功能四：多账号 + 浏览器拓展登录

### 4.1 多账号存储改造

**新建 `backend/account_store.py`**（或并入 `history_store.py` 旁的新文件）：

**目录结构（新增/迁移）**

```
%APPDATA%/Suno歌曲上传器/data/

  downloads/                         # 下载默认输出目录
  network/current_browser_token.json # 保留：首次启动迁移为默认账号，之后作废
```

**`backend.py` 改造**

- `TOKEN_FILE` 改为动态：`account_store.load_token()` / `save_token()`。
- `load_saved_token()`、`export_suno_token()` 里写 token 处改为按「当前账号」读写。
- `BROWSER_PROFILE` 改为 `APP_DATA/browser-profiles/<accountId>`；登录时按当前账号选 profile。
- 新增命令：`--accounts`（列）、`--account-add`、`--account-switch ID`、`--account-remove ID`、`--account-current`。

**架构**：Chrome MV3 扩展读用户真实浏览器的 Suno `__session` cookie → POST 到 app 本地接收服务 → 校验后写入当前账号。


### 4.3 UI 改动

- 登录区：账号下拉（当前账号高亮）+「+ 登录新账号」（走现有 CDP 登录）+「拓展登录」按钮 +「删除账号」。
- `renderer.js` 新增 `refreshAccounts()`、账号切换逻辑；`checkLogin` 改为按当前账号返回。
- 下载页与上传页在账号切换后自动刷新登录态。

### 4.4 风险

- 多账号轮换绕过限流存在 Suno 封号风险，UI 不做「自动轮换」，仅提供手动切换（把决策权留给用户，也降低风控触发面）。
- 拓展需开发者模式加载或商店分发，独立打包，**与主 exe 解耦**。
- 多 profile 会增加磁盘占用（每个 profile 数十 MB），需在 `account-remove` 时清理。

## 6. 分阶段实施顺序

| 阶段 | 内容 | 依赖 | 验收 |
|---|---|---|---|
| A | 功能一（批量队列）+ 功能二（调优） | 无 | 队列串行跑通 3 首；稳定模式单曲中位耗时 ≤600s |
| B | 功能三（下载+转WAV） | 无 | 曲库列出 + 批量下载 + 转 WAV 可用 |
| C | 功能四（多账号+拓展） | A 的 token 存储改造 | 双账号切换 + 拓展登录跑通 |

建议先做 A（复用率最高、风险最低），B 次之，C 单独排期。

## 7. 顶层风险清单

1. **Suno 接口/限流策略变动**：feed/upload 接口是逆向的，随时可能变；所有新命令都走 `SunoClient.api()` 统一异常处理，便于单点修复。
2. **封号风险**：多账号/自动化是灰区，保持「手动切换 + 不宣传」，降低触发面。
3. **打包体积**：已 208MB，新增 profile/下载不影响 exe 体积（都在 APPDATA 运行时目录），无需担心。
4. **合规**：「转 WAV 洗水印」只按「转码」实现与宣传，不承诺去除溯源水印。
